# Matane - プロダクト要求仕様書 (PRD)

## 1. プロダクト概要とミッション
*   **アプリ名**: Matane（マタネ）
*   **コンセプト**: 「またね」と言えるお店が、すぐ決まる。
*   **プロダクトミッション**: ATODE(Matane)は飲食店を記録するアプリではない。「次にどこへ行くか」を最短で決めるための、自分専用の飲み会コンシェルジュである。過去を保存することが目的ではなく、「未来の意思決定を支援すること」を最優先とする。
*   **対象デバイス**: スマートフォン専用（PWA / モバイルWebアプリとして利用想定）

## 2. 開発・設計の原則
開発中に迷った場合は、以下の原則と優先順位を必ず守ること。

*   **優先順位**: 未来の意思決定 ＞ 思い出の保存 ＞ データ収集
*   **原則1**: 入力を増やさない。
*   **原則2**: 人間に入力させず、自動取得（GPS, 訪問日時, 住所, 最寄り駅など）を優先する。
*   **原則3**: 「あとで入力できる」なら今は入力させない（2段階登録の徹底）。
*   **原則4**: 過去を見るためではなく、未来の意思決定を助ける機能を優先する。
*   **原則5**: 「毎回使う機能」だけを追加する。
*   **原則6**: UIは片手・親指操作を前提とする。フリック入力（キーボード）は極限まで排除。
*   **原則7**: 迷ったら機能を削る。シンプルさは機能である。

## 3. MVP（初回リリース / Phase 1）完了条件
以下の機能が実装された時点で初回リリースとする。AI機能は未実装でよい。
- [ ] 3秒以内で仮登録できる
- [ ] GPS検索が正常動作する（現在地から周辺店舗取得）
- [ ] 店名検索ができる
- [ ] 肉付け（二次登録）が1分以内で完了する
- [ ] 月別一覧表示（タイムライン）
- [ ] 店舗詳細表示
- [ ] 「今日どこ行く？」機能（ルールベースでの提案表示）

## 4. データ構造とアーキテクチャ思想
保存の単位は「店舗」ではなく「その日の訪問体験（Visits）」とする。
同じ店でも一緒に行った人や満足度は毎回変わるため、`Venues`（店舗マスター）と`Visits`（訪問履歴）の2レイヤー構造を採用する。将来的に`Wish`（行きたい店リスト）も追加予定。

### `Venues` テーブル (店舗マスタ)
| フィールド | 型 | 説明 |
| :--- | :--- | :--- |
| `id` | String | ユニークID (PK) |
| `place_id` | String | Google Places API等のプレイスID |
| `name` | String | 店名 |
| `location` | LatLng | 緯度経度 |
| `address` | String | 住所 |
| `nearest_station` | String | 最寄り駅 |
| `category` | String | `bar`(仕事での使用がメインの飲み屋) / `family`(家族での使用がメインのご飯屋・公園・スーパー等)。ホーム画面からの新規登録は一律`family`として作成され、`bar`は二次登録画面等からの編集用に残る過去互換の値 |

### `Visits` テーブル (訪問体験・履歴)
| フィールド | 型 | 説明 |
| :--- | :--- | :--- |
| `id` | String | ユニークID (PK) |
| `venue_id` | String | Venuesテーブルへの参照 (FK) |
| `visited_at` | DateTime | 訪問日時（一次登録時のタイムスタンプ） |
| `is_completed`| Boolean | 肉付け（二次登録）が完了しているか |
| `who` | List<String> | 誰と: [1人, 家族, 友人, 仕事/上司] |
| `revisit` | String | また行きたいか: [絶対行く, 機会あり, 1回でいい] |
| `budget` | String | 予算感: [〜3k, 〜5k, 〜10k, 10k〜] |
| `alcohol_tags`| List<String> | お酒の武器: [日本酒, ハイボール, ビール, その他] |
| `quietness` | String | 静かさ: [静か, 普通, ガヤガヤ] |
| `best_photo` | String | 厳選の1枚（画像URL）。1枚のみ。アップロード時リサイズ処理必須。 |
| `memo` | String | 自由入力メモ |
| `ai_tags` | List<String> | (将来用) AIによる写真解析タグ格納用。空配列で定義。 |

## 5. 画面設計とUI/UX要件

### 画面①：ホーム画面 (HOME)
記録の入口はホーム画面に「ココを記録」「名前で記録」の2つの丸ボタン（同じ色・同じサイズ、縦に並べて表示）を置く。用途カテゴリ（飲み屋/家族）の選択はトップ画面から撤廃する。新規Venueは一律`category: family`として作成する。
*   **📍ココを記録**:
    *   タップすると「名前わかる？」と店名入力欄を一瞬だけ表示し、GPS取得を進める。店名は空欄のままでもよい。
    *   「名前わかる？」の後、ダイアログを閉じずに続けて「写真を1枚」ステップへ進む。写真の選択（またはスキップ）と同時に`is_completed: true`でVisitを作成し（`who`/`revisit`/`budget`/`alcohol_tags`/`quietness`等の詳細な肉付けや、そのための二次登録画面は経由しない）、下部に5秒間「取り消す」スナックバーを表示する。来店記録(Visit)を店名だけでその場作成できる入口は、このGPSベースの「ココを記録」のみとする。
*   **🔍名前で記録**:
    *   タップすると店名入力欄のみのダイアログを開く。Visit(来店記録)は作成せず、入力に応じてGoogle Places Text Searchで店名候補を検索し、候補一覧から選ぶか入力した店名のまま「登録する」で**Venue(店舗マスタ)**を事前登録すると同時に、気になるリストへも追加する（`is_wished: true`）入口。まだ行ったことのない店を残す唯一の入口のため、登録＝気になる登録として一体化しており、別ダイアログには分けない。過去の記録・履歴の一覧表示は行わない。
    *   候補を選択した場合はplace_id・住所・位置情報付きでVenueを登録する。候補が0件、またはGoogle Places APIキー未設定・通信失敗の場合も、入力した店名のみでそのまま登録できる。選んだ候補のplace_idが既存Venueと一致する場合は重複登録せず、既存Venueをそのまま気になる登録済み扱いとする。
    *   ダイアログ内の「気になる理由（任意）」チップで理由タグを付けられる。
*   **共通**:
    *   「今日どこ行く？」カード（半年行っていないお気に入り等をルールベースで表示）。

### 画面②：二次登録/肉付け画面 (VISIT REGISTRATION)
キーボードを立ち上げず、片手（親指）が届く画面下半分〜中央での数タップで完結させる。
*   **入力項目**: 上記の`who`, `revisit`, `budget`, `alcohol_tags`, `quietness`を、ChoiceChips（選択式ボタン）で表示。
*   **ベストショット**: カメラ/ライブラリから画像選択。フロントエンド側で自動リサイズ・軽量化（最大1024px）して1枚だけをアップロード。
*   **自由メモ**: テキストエリア（音声入力推奨のプレースホルダー）。

### 画面③：振り返り・一覧画面 (TIMELINE)
*   **月別セクション**: 履歴を「2026年7月 (3回 / 平均¥4,500)」のように月別のヘッダーで区切り、季節感のある淡い背景色をつける。
*   **クイックフィルター**: 画面上部に `[🍶] [🥃] [🍺] [🍷]` のアイコンを常設。ワンタップでお酒タグによる絞り込みが可能。

### 画面④：店舗詳細画面 (VISIT DETAIL)
未来の意思決定を支援する機能を配置。
*   **店舗情報**: 過去の肉付けデータ、ベストショット、自由メモの表示。
*   **終電時刻・帰宅アラート**:
    *   店舗の最寄り駅から、「自宅」および「赴任先」への最終電車リミットを自動計算（または静的登録・API等）して表示。行き先ラベル・終電目安時刻は環境変数で個人設定可能とする。
    *   ※曜日による優先度（週末は自宅、平日は赴任先）を持たせる。

## 6. 特記事項・オフライン対応
*   **オフライン要件**: 通信不能（地下店舗など）でも利用可能であること。GPS取得後にローカルへ仮保存し、通信回復時にバックグラウンドでクラウドDBへ同期する。オフライン中でもキャッシュによる一覧表示が可能であること。
*   **写真ポリシー**: 保存は1枚のみ。将来的なAI解析（画像から寿司、カウンター等のタグ自動生成）を前提とした設計とする。
