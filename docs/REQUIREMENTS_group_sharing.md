# 場所データのグループ共有機能 - 要件定義書

## 1. 背景・目的

現状Mataneは個人専用の「飲み会コンシェルジュ」として設計されており、`Visits`（訪問履歴）は`user_id`本人のみが閲覧・編集できる完全プライベートなデータになっている。一方`Venues`（店舗マスタ）と気になるリスト（`is_wished`）は、認証済みユーザー全員に読み書きが開放された事実上のグローバル共有テーブルになっている。

本要件は、PRD記載のPhase4「家族・友人とのデータ共有」を前倒しし、まず**夫婦（将来的には家族）単位での場所・訪問記録の共有**を実現することを目的とする。

将来的に子どもなど3人以上の家族に拡張する可能性を考慮し、「夫婦2人固定」ではなく**N人のグループ**としてデータ設計を行う。

## 2. スコープ

### 共有する対象
- `Visits`（訪問履歴・メモ・写真・タグ等） — 現状は完全非公開 → グループ内で共有
- 気になるリスト（`Venues.is_wished` / `wish_reason`） — 現状は全ユーザー公開 → グループ単位に閉じる
- `Venues`（店舗マスタそのもの） — 現状は全ユーザー公開 → グループ単位に閉じる

### 共有の粒度
選択式（1件ごとに共有ON/OFF）は採用せず、**グループに所属した時点で全記録が自動的に相互に見える**方式とする。過去分・今後分とも同様に扱う（時点でのフィルタリングは行わない）。PRD原則1「入力を増やさない」に合致。

### 非スコープ（今回は実装しない）
- プッシュ通知（相手の新規登録・来店をリアルタイム通知）
- グループごとの役割・権限差（管理者/一般メンバーの機能差）
- グループ名・アイコンのカスタマイズ
- 招待コード以外の招待手段（SMS自動送信等）
- 1ユーザーが複数グループに同時所属するケース

## 3. 用語

| 用語 | 説明 |
| :--- | :--- |
| グループ | 場所・訪問記録を共有する単位。夫婦・家族を想定。1ユーザーは同時に1グループのみに所属可能 |
| メンバー | グループに所属するユーザー |
| 招待コード | 未所属ユーザーをグループに招待するための使い捨てトークン |

## 4. データモデル

### 新規テーブル

#### `groups`
| フィールド | 型 | 説明 |
| :--- | :--- | :--- |
| `id` | uuid (PK) | |
| `name` | text, nullable | 任意のグループ名（例:「〇〇家」）。MVPでは未入力可 |
| `created_by` | uuid (FK auth.users) | 作成者 |
| `created_at` | timestamptz | |

#### `group_members`
| フィールド | 型 | 説明 |
| :--- | :--- | :--- |
| `group_id` | uuid (FK groups) | |
| `user_id` | uuid (FK auth.users) | |
| `joined_at` | timestamptz | |

- PK: (`group_id`, `user_id`)
- `user_id` に UNIQUE制約を付け、1ユーザーが同時に複数グループへ所属できないようにする
- ロール（owner/member）の区別は設けない。全メンバー対等（後述の招待発行権限も全員に付与）

#### `group_invites`
| フィールド | 型 | 説明 |
| :--- | :--- | :--- |
| `id` | uuid (PK) | |
| `group_id` | uuid (FK groups) | |
| `code` | text, unique | 招待コード（URLセーフなランダム文字列） |
| `created_by` | uuid (FK auth.users) | |
| `expires_at` | timestamptz | `created_at` + 24時間 |
| `used_at` | timestamptz, nullable | 使用済みになった日時 |
| `used_by` | uuid, nullable (FK auth.users) | 使用したユーザー |
| `created_at` | timestamptz | |

- 招待コードは発行から24時間で失効、かつ1回限りの使用（`used_at`が入っていたら再利用不可）
- グループの既存メンバーは誰でも新しい招待コードを発行できる
- 未所属ユーザーが自分でグループを新規作成する（＝実質的に「招待コード発行」の起点）操作も本テーブル/`groups`作成のUIから行う

### 既存テーブルの変更

#### `visits`
スキーマ変更は不要（`group_id`のような非正規化カラムは持たない）。RLSポリシーのみ変更する。

- SELECT: `auth.uid() = user_id` **OR** 自分と行の`user_id`が同じグループに所属している場合
  ```sql
  auth.uid() = user_id
  or exists (
    select 1 from group_members gm_self
    join group_members gm_owner on gm_owner.group_id = gm_self.group_id
    where gm_self.user_id = auth.uid()
      and gm_owner.user_id = visits.user_id
  )
  ```
- INSERT: 現状維持（`auth.uid() = user_id`のみ）
- UPDATE / DELETE: 現状維持（`auth.uid() = user_id`のみ、＝作成者のみ編集・削除可）

グループ脱退・解散時は`group_members`から行が消えるだけで、上記ポリシーが即座に再評価されるため、**データの物理削除やタイムスタンプでの出し分けをしなくても自動的に非表示になる**。

#### `venues`
- SELECT / UPDATE ポリシーを「全認証ユーザー」から「`created_by`と同じグループのメンバーのみ」に変更する
  - ただし`created_by`が未所属（グループなし）の場合は本人のみが読み書きできる状態を維持
- INSERT ポリシーは現状維持（`created_by = auth.uid()`）

同一店舗を別グループが別々に登録した場合、`place_id`のグローバル重複排除は失われる（グループごとに別レコードになる）。これはプライバシーとのトレードオフとして許容する。

## 5. 画面・UI要件

### グループ設定画面（新規）
設定/メニュー導線から遷移する新規ページ。

- **未所属の場合**
  - 「グループを作る」ボタン → グループ作成 + 招待コード即発行
  - 「招待コードを持っている」→ コード入力欄 → 参加処理
- **所属している場合**
  - メンバー一覧（名前 or メールの一部などを表示）
  - 「招待コードを発行する」ボタン（既存の未使用コードがあれば併記、新規発行も可）
  - 発行したコード/リンクをOSの共有シートで送信（既存の`VenueDetailClient.tsx`の`handleShare`パターンを流用）
  - 「グループを抜ける」ボタン（確認ダイアログ必須。実行後は即座に相手の記録が見えなくなる旨を明記）

### 招待コード入力・参加フロー
1. 招待された側がアプリ内でコードを入力（またはディープリンクで直接遷移）
2. コードの有効性（未使用・期限内）をチェック
3. 参加確定 → `group_members`に追加、`group_invites.used_at`/`used_by`を更新
4. 参加後、既に所属していた場合はエラー（1ユーザー1グループ制約）

### 記録の表示区別
- タイムライン・店舗詳細で、パートナー（自分以外のメンバー）が作成した`Visit`には、誰の記録かひと目でわかる表示（名前イニシャルのアバター等）を付与する
- 自分の記録には編集・削除操作、パートナーの記録には表示のみ（編集・削除ボタンを出さない）

## 6. 権限マトリクス

| 操作 | 自分のVisit | パートナーのVisit | 自分が登録したVenue | パートナーが登録したVenue |
| :--- | :---: | :---: | :---: | :---: |
| 閲覧 | ○ | ○ | ○ | ○ |
| 新規作成 | ○ | – | ○ | – |
| 編集 | ○ | × | ○ | ○ |
| 削除 | ○ | × | ○ | ○ |

Venueの編集・削除は現行仕様（全認証ユーザーが書き込み可）を踏襲し、グループ内では引き続き双方が編集可能とする。

## 7. グループ解除フロー

- 本人が「グループを抜ける」を実行すると`group_members`から本人の行のみ削除
- 相手側のグループには影響なし（相手は引き続きグループに所属したまま。ただし2人グループの場合は相手が1人だけのグループに残る形になる）
- 解除は即時反映。過去に共有されていたVisits/Venuesは双方とも自分が作成したものは引き続き自分の手元に残るが、相手のものは即座に見えなくなる（データの削除は行わない）
- 抜けた後は新しい招待コードで別グループに入り直せる

## 8. 検討事項・オープンイシュー

1. **既存ユーザーの移行**: 本機能リリース時点で既に存在する`venues`/`visits`データの扱い。未所属ユーザーは「グループなし＝本人のみ閲覧可」として扱う想定（上記RLS設計で自然にカバーされる）
2. **招待コードの配布経路**: MVPではアプリ内のOS共有シート（LINE等への手動送信）のみ。メール自動送信は今回スコープ外
3. **グループ名の要否**: UI上「グループ」という概念をユーザーにどう見せるか（「〇〇家」等の命名を必須にするか）は画面設計時に確定させる

## 9. 実装への影響サマリー

- 新規Supabaseテーブル3つ（`groups` / `group_members` / `group_invites`）とそのRLSポリシー
- `venues` / `visits`のRLSポリシー変更
- 新規画面: グループ設定ページ、招待コード入力フロー
- 既存画面の変更: タイムライン・店舗詳細に「誰の記録か」の表示を追加、パートナーのVisitは編集不可のUIに
- ローカルDB（Dexie）側の同期ロジック（`sync.ts`）にも、グループメンバーのVisits/Venuesを取得・マージする処理の追加が必要
