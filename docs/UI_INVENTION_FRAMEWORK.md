# Matane UI発明フレームワーク

「またね」と言えるお店が、すぐ決まる――このミッションを、既存Webアプリの語彙（タブ・カード・一覧→詳細）を疑い直した上で、どこまで新しい操作原理として発明できるかを検討したドキュメント。

---

## 0. 対象プロダクトの理解

### プロダクト構造
- **目的**: 過去の記録ではなく「次にどこへ行くか」を最短で決める意思決定支援。優先順位は「未来の意思決定 ＞ 思い出の保存 ＞ データ収集」とPRDに明記されている。
- **ターゲット**: 片手・親指操作前提のスマホ専用ユーザー。仕事の飲み・家族の外食の両方を1本のアプリで扱う。
- **本質的な問題**: 「またこの店行きたいな」と思った記憶は、時間が経つと埋もれて選択肢に上がらなくなる。人はキーボード入力を面倒くさがるので、記録自体が続かない。
- **主要価値**: 3秒で仮登録できる低摩擦な記録（一次登録）と、あとから肉付けできる二段階登録。
- **最重要ユーザー行動**: 「名前で記録」「ココを記録」の2つの丸ボタンをその場で押すこと。
- **成功状態**: 「今日どこ行く？」を開いた瞬間に、行くべき店が迷わず決まること。
- **リピート理由**: 実は"記録アプリ"としてではなく、外食・飲み会のたびに"意思決定の入口"として開かれる。

### 実装構造（要点）
- Next.js App Router / Tailwind、Dexie(IndexedDB)によるオフラインファースト＋Supabase同期。
- データモデルは `Venues`（店舗マスタ、`is_wished`兼用）と `Visits`（訪問体験、`is_completed`で一次/二次登録を区別）の2層。
- 画面はホーム／あしあと(timeline)／気になる(wishlist)／わたしデータ(stats)／ちかく(map)の5タブ＋店舗詳細／訪問詳細／登録／グループ／設定。
- UI部品は `ChoiceChips`（チップ選択）、`BottomNav`（固定下部タブ）、`PlaceCandidateList`、月別グルーピングされた一覧、棒グラフ、Google Map。
- 「今日どこ行く？」はホーム画面の1枚のカードで、ルールベース（久しく行っていないお気に入り）の単一提案。

現在の実装構造は「観測対象」であり、以降の発明のための制約としては扱わない。

### 構造的な問題分析
| 観点 | 現状の課題 |
| :-- | :-- |
| 機能構造 | あしあと／気になる／ちかく／わたしデータが別タブに分断されており、同じ「店」という情報が4箇所に散らばって存在する。 |
| 認知構造 | ユーザーは「どのタブに行けばこの店の情報があったか」を覚える必要がある。フィルターチップ（カテゴリ・目的・お酒）はすべて能動的に押させる形で、システムからは何も提案してこない。 |
| 時間構造 | 「今日どこ行く？」は起動時点の静的な1枚のカードで終わり、時間経過・季節・気分の変化を表現できていない。実際には「しばらく行っていない」という時間的減衰こそがこのアプリの核心的な変数なのに、UI上は数行のテキストでしか扱われていない。 |
| 関係構造 | 誰と(who)・予算・静かさ・お酒タグは相互に関係のあるデータだが、一覧画面ではただの文字列の羅列として横並びに表示されるだけで、店同士の関係（似た店、対になる店）が可視化されない。 |

## 1. 画面を忘れる：現実世界の比喩（20案・圧縮）

各行＝ 比喩 → 対応する価値／操作の変化。

1. **庭** → 気になるリストは「植える」、時間が経つほど「収穫どき（=また行きたい）」が育つ。一覧の代わりに生育状態を見る。
2. **潮だまり** → 記録した店は潮が引くと見え、満ちると隠れる。「久しく行っていない」＝潮が引いた状態として空間的に見える。
3. **常連の記憶（バーテンダーの頭の中）** → 検索せず、文脈（誰と・気分）を伝えるだけで店が浮かぶ。メニューを引かない。
4. **足あと（すでにアプリ内の名称）** → 一覧ではなく、実際に歩いた地形の上に足跡が残る。時系列は地図上の軌跡になる。
5. **たき火を囲む夜** → 記録は「今夜の話のタネ」として時間限定で温かく提示され、翌朝には静かに畳まれる。
6. **占い・おみくじ** → 「今日どこ行く？」は選ぶのではなく引くもの。不確実性を演出に変える。
7. **潮汐表（タイドグラフ）** → 各店に満ち引きの周期があり、今が「行きどき」の店が波形として浮かぶ。
8. **星座** → 一緒に行った人・気分でつながる店同士を線で結び、星座として眺める。検索ではなく発見。
9. **お品書き（黒板メニュー）** → その日の気分に応じて店主が数件だけ書き出す。全件一覧を捨てる。
10. **手紙のやりとり** → グループ共有は「また行こうね」という手紙を送り合う行為として表現、通知ではなく往復書簡。
11. **年輪** → 店ごとの訪問回数・関係の深さを年輪として視覚化。古い店ほど厚みが増す。
12. **旅のスタンプラリー** → 未訪問（気になる）はスタンプ待ちの空欄として地図上に見え、訪問でスタンプが押される。
13. **写真の現像** → 記録は入力ではなく「現像」。撮った瞬間はまだ像が薄く、時間や肉付けで濃くなる。
14. **潮風に吹かれる凧** → 気になるリストは手を離すと風に流され、放っておくと遠ざかる（風化）。
15. **料理のコース進行** → タイムラインは月別リストでなく、一晩のコースのように前菜→メイン→〆と体験の流れで並ぶ。
16. **地層** → 過去の訪問は掘れば出てくる地層。表面には「今」だけがあり、下にスクロールでなく掘るように過去へ潜る。
17. **etch a sketch（振ると消える砂絵盤）** → 「気になる」を諦める操作は、砂を振って消す身体的なジェスチャーにする。
18. **駅の発車標** → 「今日どこ行く？」は次発・次々発のように複数候補が入れ替わりで表示され続ける。
19. **潜水艦のソナー** → ちかく画面は地図ではなく同心円のソナー表示。距離だけでなく「行きどき度」を反響として出す。
20. **結び目（縁結びの紐）** → グループのパートナーとの共有は、1本の紐に結び目が増えていくメタファーで、共有履歴そのものが視覚的資産になる。

**採用に値する軸**：②潮だまり／③常連の記憶／⑦潮汐表／⑧星座／④足あと／⑩手紙、の6つが「操作行動そのもの」を変える力を持つと判断（他は装飾止まりのため後段で不採用）。

## 2. 異分野からの操作原理の輸入（圧縮）

| 分野 | 抽出した体験原理 | Web UIへの変換 |
| :-- | :-- | :-- |
| テーマパーク | 待ち時間そのものが期待を高める演出になる | 「気になる」登録から時間が経つほど、再訪の"呼びかけ"が強くなる仕組み |
| ボードゲーム | 手番制、限られたリソースの配分 | 1日に出す「今日どこ行く？」の候補は常に3枠のみ、選ぶと次の手番まで更新されない |
| 子供の遊び（宝探し） | 全体像を見せず、手がかりから発見させる | 気になるリストは一覧でなく、ヒント（理由タグ）から店を掘り当てる探索操作 |
| 楽器 | 単音でなく組み合わせで演奏が生まれる | 「誰と×予算×静かさ」の組み合わせを同時に"弾く"と該当店が鳴る（絞り込みでなく演奏） |
| スポーツ観戦 | 実況によるリアルタイムの意味づけ | 記録時に「これは何回目の来店か」「前回よりどう変わったか」が即座に読み上げられる |
| 建築 | 導線と閾（しきい）、部屋を跨ぐ体験の連続性 | 画面遷移でなく、1つの空間内をズーム／パンして店に「近づく」操作 |
| 編集技術 | カット割りのリズム、モンタージュ | 訪問記録の羅列でなく、写真だけが連続再生されるモンタージュとしての振り返り |
| 生物の進化 | 淘汰圧・休眠・再活性化 | 使われない気になる店は自然に「休眠」し、条件が揃うと再浮上する |
| 都市設計 | 目的地でなく通り道で発見する（desire path） | ちかく画面は検索でなく、実際に歩いた経路上に自然に候補が現れる |
| 舞台演出 | 暗転と焦点、全部を見せない | 一度に1店だけスポットライトを当てて意思決定させ、他は暗闇に置く |
| ミステリーゲーム | 手がかりを集めて推理する | 「今日どこ行く？」の提案根拠（誰と・季節・久しぶり度）を推理ボードのように並べて見せる |
| 料理 | 塩梅（さじ加減）、味見しながら調整 | 絞り込みはスライダーでなく「味見」操作＝候補を仮に選んで手応えを見てから確定 |
| 映画編集 | 伏線と回収 | 「また行きたい」と言った過去の発言が、後日「今がその時」と回収される |
| 軍事戦略 | 偵察してから配置を決める | GPSでの周辺偵察→即決という「ココを記録」の骨格をそのまま拡張 |
| 自然現象（潮汐・季節） | 周期的な満ち引き、旬 | 店の「旬」を可視化し、今しか出てこない提案を作る |

## 3. 前提破壊マトリクス（代表12前提）

| 前提 | 反転／削除／空間化／時間化／自律化・身体化 | 生まれる操作原理 |
| :-- | :-- | :-- |
| ユーザーが画面を移動する | 空間化：画面でなく1つの地形をパン／ズーム | 遷移でなく「近づく」 |
| 情報は一覧表示される | 時間化：一覧でなく満ち引きで浮沈 | 検索でなく「今浮いているもの」を見る |
| ユーザーが機能を選ぶ | 自律化：システムが状況から次の一手を提示 | メニューがなくなる |
| メニューから目的地へ移動する | 削除：目的地の概念自体をなくす | 常に今いる文脈の延長で次が現れる |
| 過去の操作は戻ることで扱う | 連続化：戻る＝時間を巻き戻す演出に統合 | Backボタンの消滅 |
| データは読むもの | 能動化：データがユーザーに働きかける | 通知でなく「呼びかけ」 |
| 状態は表示するもの | 身体化：状態はジェスチャーで感じ取るもの | 数値でなく手応え |
| ユーザーが検索する | 反転：店がユーザーを見つける（文脈一致） | 検索窓の消滅 |
| 操作には開始と終了がある | 連続化：開始・終了を消し常時進行形にする | 「保存」ボタンの消滅 |
| 記録は入力するもの | 反転：記録は現像されるもの（時間で完成） | 一次登録＝仮の像、時間で像が濃くなる |
| 一覧はソート可能な表である | 空間化：ソートでなく地形の高低差 | 並び替えUIの消滅 |
| グループ共有は閲覧権限の話である | 能動化：共有は一方向の閲覧でなく往復の合図 | 「また行こうね」の相互確認 |

## 4. 画面遷移の破壊（検討結果）

現状は5タブ＋詳細画面の「場所を移動するUI」。これを「状態が変化するUI」へ倒す場合、最大の障害は**Google Mapという外部iframe的コンポーネント**と**フォーム入力（二次登録）**の2つ。地図とフォームは「場所」の概念と相性が良いため完全排除は現実的でない。したがって、**タブ間の移動を「地形内のズームレベル変化」に置き換える案（D案）**と、**メニューという概念自体を捨てて常に"今の一手"だけを出す案（A案・B案）**の2方向を並行して検討する。

## 6. 強制発散フェーズ（30案・要約テーブル）

比率: 実用10／奇妙10／大胆5／非UI5。

**実用系（10）**
1. 二問収束フィルター（B案の原型）
2. 月別リストを「濃淡マップ」に置換
3. 気になるリストへの「風化」タイマー表示
4. 訪問直後の1タップ「またね」ボタン
5. お酒タグをスライダーでなく味見トグルに
6. GPS即記録に「近くの気になる店」を割り込ませる
7. 終電アラートをホームに先出しする常設バー
8. グループの「また行こうね」既読ならぬ既承認バッジ
9. 統計を棒グラフでなく年輪リングに
10. 気になるリストのインポートをドラッグ&ドロップの束ねる操作に

**やや奇妙（10）**
11. 店を「呼吸」させる（訪問頻度で拡大縮小するアイコン）
12. 記録はテキストでなく色を塗る操作（満足度＝色の濃さ）
13. 気になる店を手放すと画面から実際に「飛んでいく」
14. 「今日どこ行く？」をおみくじのように引く動作にする
15. 訪問記録をスタンプの押印アニメーションにする
16. 店同士を糸でつなぐ関係マップ
17. 記録画面にBGM代わりの環境音（居酒屋のガヤ音）
18. 訪問直後、写真が徐々に「現像」されるアニメーション
19. 終電時刻に応じて画面全体の色温度が変わる
20. 気になる店リストを「引き出し」として物理的に開閉する

**非常に大胆（5）**
21. タブ・画面遷移を全廃し、1枚の地形だけで全機能を完結させる（A案の原型）
22. 記録行為をやめ、GPS常時トラッキングから自動で訪問を検出する
23. パートナーと「同時にスマホを振る」ジェスチャーで合流を記録
24. 店の「旬」をAIでなく単純な経過日数の波形として常時鳴らす（音として）
25. 全データを「1年を1周する円環カレンダー」上だけで扱う

**一見UIに見えない（5）**
26. ホーム画面全体が刻々変化する潮位グラフそのもの
27. アプリを開くと最初に見えるのは地図でもリストでもなく「今日の一言」だけ
28. 訪問記録がすべて手書き風の一筆書き軌跡として蓄積される
29. 「気になる」は星座早見盤のような回転ディスクUI
30. 設定画面が存在せず、すべてがジェスチャーの「癖」として学習される

## 7. コンセプト融合（10組・要約）

| 組み合わせ | 衝突理由 | 融合後の新原理 |
| :-- | :-- | :-- |
| ①潮の満ち引き × ⑧おみくじ | 前者は連続的、後者は離散的 | 潮位が高まるほど「引き」の確率が上がる――待つほど当たりやすいおみくじ |
| ②星座マップ × ⑤味見トグル | 前者は俯瞰、後者は近接操作 | 味見トグルを動かすと星座の形そのものが再配置される＝条件変更が空間の形を変える |
| ③二問収束 × ⑨年輪 | 前者は絞り込み、後者は蓄積の可視化 | 2問答えるたびに年輪の該当層がハイライトされ、絞り込み＝過去を掘る行為になる |
| ④またねボタン × ⑳結び目 | 前者は単発、後者は蓄積 | 「またね」を押すたびにパートナーとの紐に結び目が増え、関係の厚みが見える |
| ⑥GPS即記録 × ⑫呼吸するアイコン | 前者は瞬間、後者は持続 | 記録した瞬間、地図上のその場所が"息を吸う"ように拡大し、そのまま常駐する店になる |
| ⑦終電色温度 × ①潮位グラフ | 前者は個別画面、後者は全体基調 | 終電が近づくと潮位全体の色温度が変わり、画面全体が「そろそろ」を体感させる |
| ⑩ソナー(ちかく) × ⑬砂絵盤(手放す) | 前者は探知、後者は消去 | 気になる店を手放すとソナーの反響が一つ静かに消える演出になる |
| ⑪地層 × ㉗今日の一言 | 前者は過去、後者は現在 | 「今日の一言」は地層の一番上の層で、下にスクロールでなく掘ると過去の一言が出る |
| ⑭現像アニメ × ③二問収束 | 前者は結果表示、後者は入力 | 二問に答えるたびに、写真が少しずつ現像されていく＝入力が記録を"完成させる"行為として体感される |
| ⑮お品書き × ⑨料理コース進行 | 前者は提示、後者は時間進行 | タイムラインが黒板の書き換えとして進行し、月替わりで「お品書き」がめくれる |

## 8. 新規性の監査

| 候補 | 既存UIパターンに見えないか | Level |
| :-- | :-- | :-- |
| A: 潮の満ち引き地形（タブ全廃・空間統合） | 地図アプリではない。可視化を消してもタブ構造の消滅という操作原理が残る | **Level 3** |
| B: 二問収束（連続的二択で1店へ収束） | Tinder的スワイプに見えるが「ブラウズでなく収束して1件に確定する」点でカード送りと異なる。アニメーションを消しても収束構造が残る | **Level 3** |
| C: またねの合図（別れ際の儀式化＋相互確認） | フォーム入力の言い換えに見えかねないが、「入力のトリガーが"店を出る"という物理的な別れの瞬間である」点と「相互確認（往復）」がAI/装飾を抜いても残る | **Level 2→再検証で Level 3**（後述） |
| D: 地形統合（Map/Timeline/Wishlistの単一化） | 見た目は地図アプリの応用に近く、単独では Level 2 寄り。ただし「状態が高低差として符号化される」点を残せば Level 3 の核を持つ | **Level 2〜3の境界（実装ROI優先で採用）** |

C案は「フォームの言い換え」で片付けられないよう、⑫の実装詳細（後述③）で「合図が届くまでは記録が完成しない」という**双方向性**を核に据えることで Level 3 の要件（既存サービスに名前が浮かばない操作）を満たす。

## 9. 容赦なく殺す（スコアリング）

0〜10点、括弧内は最大の欠点。

## 11. 最終4案の詳細設計

### A. 潮目（しおめ） — 記憶の潮汐UI

**② 一言で説明**
> 「潮だまりを覗き込むように、行きたい店が満ち引きするUI」

**③ 核となる発明**
- 従来のUI：5つのタブ（ホーム/あしあと/気になる/わたしデータ/ちかく）を行き来して情報を集める。
- このUI：タブが存在せず、1枚の「潮位フィールド」に全ての店が浮沈し、ユーザーはズーム/パンだけで全てにアクセスする。
- 破壊した前提：「情報は画面ごとに分割して置かれるもの」という前提。

**④ ユーザーの最初の10秒**
- 0〜3秒：起動直後、画面いっぱいに淡いブルーグレーの"水面"が広がり、いくつかの店名タグがゆっくり浮き沈みしているのを認識する。
- 3〜7秒：気になる店のタグが一番高く浮いているのを見て、指で触れてみる（何が起きるか試す）。
- 7〜10秒：触れた店がフッと持ち上がり、店名・最後に行った日・「そろそろ」という一言が浮かび上がることで、"これは訪問候補が自然に浮いてくる場所だ"と理解する。

**⑤ 操作モデル**
- 見るもの：常時変化する潮位フィールド（高さ＝行きどき度＝最終訪問からの経過×好みの重み）。
- 触れるもの：浮いているタグをつまんで引き上げる（決定）／下に押し沈める（今回は見送り＝スヌーズ）。
- 選ぶもの：ピンチズームで「あしあと（過去）」の深さへ潜る／逆にズームアウトで「気になる（未来）」の水面上へ浮上する。
- 直接操作しないもの：並び替え・フィルターのUIコントロール自体。
- システムが推測するもの：どの店を高く浮かせるか（経過日数・曜日・グループの動き）。
- 状態変化：記録を追加すると新しい浮きが1つ生まれ、時間経過で高度が変わる。
- フィードバック：つまむと波紋が広がり、周辺の浮きの高さも微妙に揺れる（関連店の示唆）。

**⑥ 情報構造**
- 情報空間：1つの連続した潮位フィールド（Z軸=時間的接近度、XY=地理的位置）。
- 状態：各店＝浮き（buoy）オブジェクトの高度・揺れ幅・色温度。
- 操作：つまむ／沈める／ズーム。
- コンテキスト：現在のズーム深度そのものが「過去⇄未来」の文脈。
- 状態遷移：浮きを引き上げる＝訪問記録の作成フローへの合流（浮きがそのまま入力カードに変形）。
- 記憶：ユーザーは"あのへんに沈んでた店"という空間的位置で店を覚える。
- 復帰方法：ホームボタン＝現在の潮位（今の水面）へスナップして戻る。

**⑦ 主要ユーザーフロー（3つ）**
1. 浮きをつまむ → 波紋が広がり関連する浮きが震える → 店カードが展開する → 「行く／また今度」の二択が現れる
2. GPS即記録（ピン留めジェスチャー：画面を長押し） → その場に新しい浮きが生まれる → 浮きが徐々に色濃くなる（現像演出） → 完了
3. ズームアウトして水面上（気になる）へ → 風化しかけた浮き（色褪せ）を見つける → つまんで持ち上げる → 「まだ気になる／手放す」の選択で風化を止めるか手放す

**⑧ 既存UIとの比較**
- 操作数：最短ルート（浮きに触れて店を見る）は1タップでタブ移動なし。ただし特定の店を"探す"操作は現行の検索より遅くなりうる。
- 認知負荷：初見は高いが、慣れると"高いところにあるもの＝今行くべき店"という単一ルールで完結。
- コンテキスト維持：常に同一空間内のため、タブ間で文脈を失わない。
- 学習コスト：高い（潜在的な最大の欠点）。
- 継続利用性：毎回眺めが変わるため飽きにくい。
- 新規性：既存サービスに類似物なし。

**⑨ なぜ今まで一般化していなかったのか**
- 技術的理由：連続的な物理シミュレーション（浮力・揺れ）をモバイルで軽量に描画するのは近年のCanvas/WebGL最適化とデバイス性能向上で初めて実用域に入った。
- ビジネス上の理由：検索・一覧・タブは実装コストが低く、A/Bテストで安全に改善できるためプロダクト側が投資しにくい。
- UX上のリスク：初見理解可能性が低く、離脱リスクが高いため多くのチームがリスクを取らない。
- 教育コスト：オンボーディングなしでは使い方がわからない。
- 従来のWeb設計との相性：SEO・ディープリンク・ブラウザバックとの相性が悪く、Webの標準的な作法（URL＝状態）と衝突する。

**⑩ 模倣された場合に何が残るか**
- 色・浮きのアニメーション・波紋エフェクトをコピーされても、「経過時間と好みの重みを高度という単一の物理量に統合し、画面遷移ゼロで全機能を完結させる」という情報設計そのものは、そのプロダクトのデータモデル（Venues/Visitsの2層構造、is_completedによる仮登録概念）と密結合しているため簡単には移植できない。

**⑪ 実装ロードマップ**
- **MVP**：ホーム画面のみを潮位フィールド化（他タブは現状維持）。データは既存の`useSuggestedVenue`相当のロジックを流用し、浮きは5〜10個程度に限定。検証項目：「タップだけで行きたい店に辿り着けるか」。成功条件：初見ユーザーの80%が3回以内のタップで店カードを開ける。
- **Version 1**：あしあと・気になるをズーム深度に統合し、タブを2つ（ホーム統合フィールド／設定）まで削減。検証：既存タブ利用の代替として離脱率が悪化しないか。
- **Ultimate Vision**：ちかく（地図）・わたしデータ（統計）も同一フィールドの別ズーム層として統合し、URLは1つ、画面遷移0の単一ページアプリになる。

**⑫ 現在の技術スタックへの落とし込み**
- コンポーネント構成：`TideField`（Canvas/SVGベースの単一コンポーネント）＋`Buoy`（店1件＝1オブジェクト）。既存の`ChoiceChips`等はBuoy展開時のカード内でそのまま再利用可能。
- 状態管理：`buoyHeight = f(daysSinceLastVisit, revisitPreference, groupActivity)` を Dexie の live query から派生させ、`requestAnimationFrame`ベースで滑らかに補間。
- URL/ルーティング：Next.jsのApp Router上は`/`単一ルートを維持しつつ、ズーム深度をクエリパラメータ(`?depth=`)で表現し、ブラウザバックと最低限整合させる。
- パフォーマンス：浮きの数が数百件規模になった際の間引き（画面外カリング）が必須。
- アクセシビリティ：潮位フィールドと並行して、スクリーンリーダー利用者には現行のリストUIをそのままフォールバック提供する（"見た目の発明"と"情報アクセス"を分離する設計）。
- モバイル対応：タッチジェスチャー（つまむ／沈める／ピンチズーム）はPointer Eventsで実装、iOSのセーフエリアはBottomNav同様`env(safe-area-inset-bottom)`を踏襲。
- **維持すべき部分**：Venues/Visitsの2層データモデル、オフラインファーストの同期ロジック、二次登録フォーム自体（Buoy展開先として再利用）。
- **捨てるべき部分**：BottomNavという「タブ」概念、月別リストという「ページネーション」概念。

### B. ふたこと確認 — 二問収束チューザー

**② 一言で説明**
> 「福引きの抽選機のように、二問答えるだけで今日行く店が1つに絞れるUI」

**③ 核となる発明**
- 従来のUI：「今日どこ行く？」は起動時の静的な1枚のカードで、根拠も1件のみ、ユーザーの今の状況（誰と／気分）を一切聞かない。
- このUI：ホームの2つの丸ボタンとは別に、「今夜、誰と？」「今日の気分は？」の**二択を連続で答えるだけ**で、既存の`who`/`budget`/`quietness`/`alcohol_tags`データに基づき候補が絞られ、最終的に1店へ収束する。ブラウジング（送り読み）ではなく、**答えるたびに選択肢が消えていく収束構造**。
- 破壊した前提：「ユーザーが機能を選ぶ・検索する」という前提を、「システムが2つの質問だけで意思決定を代行する」に置き換える。

**④ ユーザーの最初の10秒**
- 0〜3秒：ホームの「今日どこ行く？」カードをタップすると、リストではなく大きな1問「誰と行く？」が画面いっぱいに現れる。
- 3〜7秒：左右に「1人／家族・友人」の二択が表示され、直感的に選ぶ。選んだ瞬間、候補店数が「12件→5件」のようにカウントダウンする。
- 7〜10秒：続けて「今日の気分は？（静か／賑やか）」が出て選ぶと、候補が1〜2件に収束し、店名がカードとして提示される――ここで"検索していないのに決まった"ことに気づく。

**⑤ 操作モデル**
- 見るもの：質問と、背景にうっすら透ける「残り候補数」のカウンター。
- 触れるもの：二択のうち一方（大きなタップ領域、フリック可）。
- 選ぶもの：最大2問（多くても3問）。
- 直接操作しないもの：店名の一覧・検索窓・並び替え。
- システムが推測するもの：どの2軸を質問すべきか（budgetを聞くべきかquietnessを聞くべきかは、候補群の分散が最も大きい軸を動的に選ぶ）。
- 状態変化：質問に答えるたびに候補プールが可視的に収束するアニメーション（数字のカウントダウン＋候補カードが重なって減っていく）。
- フィードバック：最終1件になった瞬間、地図上の位置・終電情報・過去の記録が一気に展開される「回答」画面になる。

**⑥ 情報構造**
- 情報空間：Venues×Visitsの属性空間（who/budget/quietness/alcohol/revisit/経過日数）そのものをUI化したもの。
- 状態：現在の候補プール（Set of Venue）。
- 操作：二択への回答。
- コンテキスト：質問順序＝残りの候補群の分散が一番大きい軸を都度選び直す（決め打ちの質問順にしない）。
- 状態遷移：候補が1件になった時点で店舗詳細相当の画面へ自然遷移。
- 記憶：ユーザーは「あの時2問で当てた」という体験として覚える。
- 復帰方法：ホームへ戻ればいつでも新しい二問セッションを開始できる（履歴は残さない、都度リセット）。

**⑦ 主要ユーザーフロー（3つ）**
1. 「今日どこ行く？」タップ → Q1「誰と？」回答 → 候補収束アニメーション → Q2「気分は？」回答 → 1件に収束 → 店舗カード表示＋「決定（気になるから外す／あしあとへ）」ボタン
2. 候補が0件になった場合 → 「条件に合う店がまだありません」→ その場で「気になるに追加する」導線（新規開拓のきっかけに変換）
3. グループ利用時 → Q1の後、パートナーが同時に別の端末で回答していた場合 → 両者の回答の共通集合で収束（誰と＝一致するため自動スキップ、気分だけ両者に質問）

**⑧ 既存UIとの比較**
- 操作数：現行は「今日どこ行く？」カード→店舗詳細タップの2操作で常に同じ1件しか出ないのに対し、本案は2〜3タップだが**毎回状況に応じた別の答え**が出る。
- 認知負荷：低い（YES/NOに近い二択の連続）。
- コンテキスト維持：質問→回答→結果が1画面内の連続アニメーションで完結し、画面遷移を感じさせない。
- 学習コスト：ほぼゼロ（二択タップのみ）。
- 継続利用性：高い（answer castが解説動画のように毎回体験として楽しい）。
- 新規性：既存の「条件検索フォーム」と混同されないよう、**フォームでなく質問の連続**として設計する点が鍵（後述の監査参照）。

**⑨ なぜ今まで一般化していなかったのか**
- 技術的理由：特別な技術は不要（実装容易性が高い）。
- ビジネス上の理由：多くのアプリは「候補を絞る」ことより「候補を多く見せる」ことを広告収益や店舗掲載ビジネスの都合で優先しがちで、**1件に収束させて終わり**という設計は送客型ビジネスと相性が悪い。Mataneは個人の意思決定支援が目的のため、この制約から自由。
- UXリスク：条件を聞きすぎるとただのフィルターフォームに退化するリスクがあり、"最大2問"という制約設計が難しい。
- 教育コスト：低い。
- 従来のWeb設計との相性：良い（通常のNext.jsルーティングでも十分実装できる）。

**⑩ 模倣された場合に何が残るか**
- 二択UIやカウントダウン演出は模倣できても、「どの2軸を聞くかを候補プールの分散から動的に選ぶ」というアルゴリズムと、Mataneが既に持つ`who`/`budget`/`quietness`/`alcohol_tags`という**入力コストゼロで既に蓄積された行動データ**の厚みは、後発が同じ精度で再現するには同じだけの記録データの蓄積期間が必要になる。データこそが模倣耐性。

**⑪ 実装ロードマップ**
- **MVP**：既存の「今日どこ行く？」カードのタップ先を、固定2問（誰と／静かさ）の二択フローに置き換える。ロジックは`src/lib/db/queries.ts`の`useSuggestedVenue`を拡張。検証：2問で1件に収束する体験が「便利」と感じられるか、収束0件時の離脱率。成功条件：Q2完了率70%以上。
- **Version 1**：質問軸を動的選択（分散最大の軸を選ぶ）に高度化し、グループ共有時の同時回答マージに対応。
- **Ultimate Vision**：位置情報・時間帯・天候まで質問軸の候補に加え、"聞かれなくても分かる"領域を広げていく（ただし新規入力は増やさない原則を厳守し、既存の自動取得データのみを使う）。

**⑫ 現在の技術スタックへの落とし込み**
- コンポーネント構成：`TwoQuestionChooser`（質問カード＋収束アニメーション）を新規追加、既存の`ChoiceChips`をベースにした二択専用の大型タップ版として派生。
- 状態管理：候補プールはReactのuseStateでVenue[]を保持し、Dexieの`useTimelineVisits`/`useWishedVenues`から属性データを引く。分散計算は軽量な純粋関数（`lib/stats.ts`に近い場所へ追加）。
- 状態遷移モデル：`idle → asking(Q1) → asking(Q2) → resolved(1 venue) | empty`のシンプルな有限状態機械。
- データモデル：変更不要（既存の`Visit`/`Venue`属性をそのまま利用）。
- URL/ルーティング：`/`からモーダル的に開始し、URLは変更しない（ホームの拡張として扱う）。
- パフォーマンス：候補数が少ない（個人の記録アプリのため数百件規模）ためクライアント側計算で十分。
- アクセシビリティ：二択ボタンは`aria-pressed`と大きなタップ領域（現行の`ChoiceChips`と同水準）を踏襲、スクリーンリーダーでも質問文と残り候補数を読み上げる。
- モバイル対応：フリックジェスチャーはオプション扱いとし、タップのみでも完結する設計にする（誤操作防止）。
- **維持すべき部分**：既存の属性データモデル・チップUIの視覚言語（amber-400のアクセントカラー等）。
- **捨てるべき部分**：「今日どこ行く？」カードの単一提案ロジック（ルールベースの1件出し）。

### C. またね、の合図

**② 一言で説明**
> 「店を出る瞬間の"またね"を、そのまま記録の完成トリガーにするUI」

**③ 核となる発明**
- 従来のUI：記録は「入力するもの」であり、フォームを開いて情報を埋めて保存ボタンを押す行為。
- このUI：記録の起点は**「店を出る」という物理的な別れの瞬間**そのもの。ホーム画面ではなく、店を出た合図（大きな「またね」ボタン、またはGPSが店舗圏外に出たことの検知）が記録の開始トリガーになり、しかもグループ利用時は**パートナーの合図と自分の合図が揃って初めて記録が"確定"する**（片方だけでは仮の状態のまま）。
- 破壊した前提：「記録は個人が入力して完結するもの」という前提を、「記録は関係者間の相互確認で完成するもの」に置き換える。

**④ ユーザーの最初の10秒**
- 0〜3秒：店を出た後（または帰り道で）ホームを開くと、通常の丸ボタンの上に、少し違う質感の「またね」という大きなボタンが浮かんでいることに気づく（今しがた位置情報が店舗から離れたことをトリガーに表示）。
- 3〜7秒：押すと、店名・時間が自動で埋まったカードが現れ、「また行く？」の一言だけを聞かれる（3択：絶対行く／機会あり／1回でいい）。
- 7〜10秒：グループ利用中なら、「〇〇さんにも聞いてみる」という送信演出が流れ、相手が答えると2人分の「またね」が重なって初めてカードに封蝋のようなスタンプが押される――これが記録の完成を意味すると理解する。

**⑤ 操作モデル**
- 見るもの：店舗圏外離脱時にだけ現れる「またね」ボタン。
- 触れるもの：ボタン1つ＋revisitの3択のみ（who/budget等は自動推定か後回し）。
- 選ぶもの：また行きたいかどうかの温度感のみ。
- 直接操作しないもの：店名入力（GPSと既存Venueから自動解決）、写真（後から追加できるオプション扱いに格下げ）。
- システムが推測するもの：滞在時間から「今回はどのくらいの体験だったか」の重み付け。
- 状態変化：自分の合図＝仮封、相手の合図が揃う＝本封（グループなし利用時は自分の合図のみで即本封）。
- フィードバック：本封になった瞬間、あしあと(タイムライン)にその記録が実体化して現れる演出。

**⑥ 情報構造**
- 情報空間：位置情報の「店舗圏内⇄圏外」という2状態と、記録の「仮封⇄本封」という2状態の掛け合わせ。
- 状態：Visitに`is_completed`とは別に「相互確認待ち」の中間状態を追加（グループ利用時のみ）。
- 操作：ボタン押下＋3択。
- コンテキスト：直前にいた場所（Geofence）。
- 状態遷移：圏内→圏外検知→ボタン出現→回答→（グループなら）相手待ち→本封。
- 記憶：ユーザーは「あの店を出た瞬間に押した」という身体的なタイミングで記録を覚える。
- 復帰方法：ボタンを見逃した場合は、ホームの丸ボタン「名前で記録」から通常の二次登録フローにフォールバックできる（発明したUIが唯一の入口にならないようにする）。

**⑦ 主要ユーザーフロー（3つ）**
1. 店を出る → GPSが圏外検知 → 「またね」ボタン出現 → タップ → revisit3択回答 → （個人利用）即座に本封 → タイムラインに反映
2. グループ利用 → 自分が回答 → 相手に「またね、聞いてみる？」の送信演出 → 相手が数時間後に回答 → 2人分揃って本封＋"結び目"が1つ増える演出
3. ボタンを見逃す／圏外検知に失敗（電波不良等） → 従来通りホームの「名前で記録」「ココを記録」から手動記録が可能（フォールバック）

**⑧ 既存UIとの比較**
- 操作数：最短1タップ＋1選択（現行の二次登録フォームより大幅に少ない）。
- 認知負荷：低い（フォームでなく気持ちを1つ選ぶだけ）。
- コンテキスト維持：店を出た瞬間という文脈をそのままUIのトリガーにするため文脈の分断がない。
- 学習コスト：低い（ボタンが出た時に押すだけ）。
- 継続利用性：情緒的な満足感（"またね"のやり取り）がリピート動機になる。
- 新規性：フォーム入力の言い換えに見えないよう、**相互確認（自分だけでは完成しない）**という構造を必須要件とする。

**⑨ なぜ今まで一般化していなかったのか**
- 技術的理由：ジオフェンス検知（圏外離脱トリガー）はバックグラウンド位置情報の権限・バッテリー消費の制約が強く、PWAでは特にiOS Safariの制限が厳しい。
- ビジネス上の理由：多くの飲食店アプリは店舗送客（クーポン起点）が収益源のため、「店を出た後」に価値を出すUIへの投資インセンティブが働きにくい。
- UXリスク：位置情報の常時許可を求めることへのユーザー抵抗、誤検知（信号待ちで圏外判定される等）のリスク。
- 教育コスト：ボタンが出るタイミングの説明が必要。
- 従来のWeb設計との相性：PWAのバックグラウンド処理制約と相性が悪く、ネイティブアプリの方が実現しやすい領域。

**⑩ 模倣された場合に何が残るか**
- 「店を出たら通知」自体は模倣可能だが、**Mataneというプロダクト名＝「またね」という言葉の意味そのものと操作原理が完全一致している**点は、ブランド名を変えずにコピーすることができない。また相互確認という関係性データ（グループ機能と一体化した設計）は単体の通知機能として切り出しても意味を失う。

**⑪ 実装ロードマップ**
- **MVP**：ジオフェンス検知を使わず、まず「今いる場所から一定時間・一定距離離れたら」を**アプリを開いたタイミングでの簡易判定**（前回のCheck-in位置との距離＋経過時間）に代替し、ホーム画面に「さっきの〇〇、またね？」バーとして表示する。検証：ボタンのタップ率、revisit回答完了率。成功条件：GPS即記録（ココを記録）ユーザーの半数以上がこのバー経由でrevisitを回答する。
- **Version 1**：Web Push通知＋簡易ジオフェンス（Geolocation APIのwatchPositionで圏外相当を判定）を追加し、グループの相互確認フローを実装。
- **Ultimate Vision**：ネイティブアプリ化してBackground Geolocationを使い、本当の意味で「店を出た瞬間」を検知、結び目の可視化（年輪・星座的表現）と統合。

**⑫ 現在の技術スタックへの落とし込み**
- コンポーネント構成：`MatanePrompt`（ホーム上部の呼びかけバー）、既存の`ChoiceChips`のrevisitオプションをそのまま再利用。
- 状態管理：`Visit`に`confirmation: "self" | "mutual" | null`のような中間状態を追加（グループ利用時のみ使用、既存スキーマへの追加のみで破壊的変更なし）。
- データモデル：`group_members`テーブルは既存のグループ共有機能をそのまま活用でき新規テーブル不要。
- アニメーション：CSS Transition程度の軽量な"重なる封蝋"演出（Framer Motion等を新規導入するかは実装コスト次第）。
- ジェスチャー：ボタン押下のみ、複雑なジェスチャーは要さない。
- URL/ルーティング：ホーム画面内で完結、新規ルート不要。
- パフォーマンス：位置比較はローカル計算のみで軽量。
- アクセシビリティ：バーはテキストで明示し、位置情報検知に依存しない代替導線（既存の「名前で記録」フロー）を常に残す。
- モバイル対応：バックグラウンド処理はPWAの制約内でベストエフォート、フォールバックを前提に設計。
- **維持すべき部分**：Visit/Venueスキーマ、二次登録フォーム（詳細を後から足したい人向けに残す）、グループ機能のRLS設計。
- **捨てるべき部分**：「二次登録は必ずフォーム画面に遷移する」という前提（revisitだけならその場で完結させる）。

### D. 地形としてのちかく

**② 一言で説明**
> 「距離ではなく"今のあなたとの関係"で地形の高さが変わる地図UI」

**③ 核となる発明**
- 従来のUI：ちかく(地図)・あしあと(時系列リスト)・気になる(リスト)は別タブの別データビューであり、同じ店の情報がタブごとに違う切り口で重複して存在する。
- このUI：3画面を1つの地図ベースの空間に統合し、**距離を横位置、関係性（訪問済み／気になる／久しぶり度）を縦の高低差（等高線・色）としてエンコード**する。近いから逆に行き慣れて色褪せて見える店と、少し遠いが「気になる」ため輝いて見える店が、地図上で直感的に区別できる。
- 破壊した前提：「地図＝距離順に並べるもの」「一覧＝カテゴリ別に分けるもの」という前提を「地図＝関係性の濃淡地形」に統合。

**④ ユーザーの最初の10秒**
- 0〜3秒：ちかく画面を開くと、これまでの地図に加え、地面がわずかに凹凸のある陰影（等高線）で覆われていることに気づく。
- 3〜7秒：自分の現在地の近くで、ひときわ明るく浮き上がっているピンをタップしてみる。
- 7〜10秒：それが「気になるリストに入れて3ヶ月経つ店」だと分かり、"高さ＝行くべき度"というルールを直感的に理解する。

**⑤ 操作モデル**
- 見るもの：Google Map上に重ねた高低差レイヤー（気になる度・久しぶり度をヒートマップ的に着色）。
- 触れるもの：ピン、地形の凹凸自体（ズーム）。
- 選ぶもの：現行のフィルター（訪問済み／気になる）は残しつつ、デフォルトは「すべて高低差で表示」。
- 直接操作しないもの：ソート順（距離順ソートという操作をなくし、地形の見た目そのものが優先順位を表す）。
- システムが推測するもの：どの店を高く（目立たせて）表示するか。
- 状態変化：訪問すると即座にその店の"標高"がリセットされ、低くなる（行ったばかり＝急がなくていい）。
- フィードバック：地図をピンチすると、あしあとのタイムラインが同じ画面の下からせり上がってくる（別タブでなく同一画面の連続ズーム）。

**⑥ 情報構造**
- 情報空間：地理座標×関係性スコアの2.5次元マップ。
- 状態：各Venueの標高値＝f(気になる度, 経過日数, 距離)。
- 操作：ピン選択、ピンチズーム（地図⇄タイムラインの連続遷移）。
- コンテキスト：現在地。
- 状態遷移：ズームアウト＝空間的俯瞰、ズームイン＝個別店舗詳細、さらに下端までズームすると時系列（あしあと）へ連続的に移行。
- 記憶：「あのへんが高く光ってた」という空間記憶。
- 復帰方法：ボトムナビの「ちかく」タップでこの統合画面へ戻る（他タブは当面維持しつつ段階的に統合）。

**⑦ 主要ユーザーフロー（3つ）**
1. ちかく画面を開く → 高く光るピンに気づく → タップ → 店カード展開（気になる度・経路） → 「あしあとへ記録」導線
2. 地図をピンチダウン(縮小操作の逆) → 画面下からタイムラインが連続的にせり上がる → そのままスクロールで過去の記録を閲覧 → 再度ピンチで地図へ戻る
3. 位置情報オフライン時 → 従来通りリストへフォールバック（高低差は「気になる度バッジ」として簡易表現に縮退）

**⑧ 既存UIとの比較**
- 操作数：ちかく・気になる・あしあとの行き来がタブ切り替え(1操作×複数回)からズーム操作(連続的)に変わり、体感の遷移コストが下がる。
- 認知負荷：既存の地図UIの延長のため学習コストは低い。
- コンテキスト維持：地図という共通の器の中で完結するため高い。
- 学習コスト：低い（4案中最も低い）。
- 継続利用性：中程度（新規性はA/B/Cほど強くない）。
- 新規性：地図アプリの応用に見えるリスクがあるため、高低差エンコーディングの一貫性が生命線。

**⑨ なぜ今まで一般化していなかったのか**
- 技術的理由：Google Maps JavaScript APIの上にカスタムレイヤー（オーバーレイ）を重ねる実装は可能だが、パフォーマンスチューニングが必要。
- ビジネス上の理由：地図SaaSの多くは店舗掲載ビジネス前提で、個人の関係性データ（気になる度・経過日数）をレイヤー化する発想自体が既存の地図UIの外側にある。
- UXリスク：地図に情報を詰め込みすぎると単に見づらくなるリスク。
- 教育コスト：低い。
- 従来のWeb設計との相性：良い（既存のMapClient.tsxを拡張する形で実装できる）。

**⑩ 模倣された場合に何が残るか**
- 地図に何かを重ねる表現自体は模倣されやすいが、**距離・気になる度・経過日数を1つの標高値に統合する重み付けロジック**と、そのデータ源（Matane固有のVisits/Wishデータ）は他社が同じ精度で再現するには同種のデータ蓄積が必要。

**⑪ 実装ロードマップ**
- **MVP**：既存の`MapClient.tsx`にヒートマップ風オーバーレイ（Google Maps の`HeatmapLayer`相当、または簡易な円グラデーション）を追加し、「気になる度×経過日数」で色分けするだけに留める（等高線の物理的な凹凸表現はVersion 1以降）。検証：色分け表示ありのちかく画面で、気になる店への遷移率が現行のリスト表示より上がるか。成功条件：ちかく画面経由の店舗詳細遷移率+20%。
- **Version 1**：ピンチズームでタイムラインへ連続的に移行するインタラクションを実装し、あしあとタブとちかくタブを実質統合、BottomNavのタブ数を4つに削減。
- **Ultimate Vision**：わたしデータ(統計)もこの地形の"断面図"として同一空間に統合し、5タブ構造を「ホーム／統合地形／設定」の3構造まで簡素化する。

**⑫ 現在の技術スタックへの落とし込み**
- コンポーネント構成：既存`MapClient.tsx`を拡張し`RelationHeatLayer`を追加。
- 状態管理：標高値の計算はpureな関数として`lib/stats.ts`と同じ層に追加、Dexieのlive queryから導出。
- 状態遷移モデル：`zoomLevel`をURLクエリではなくローカルstateで管理し、一定閾値を超えたらタイムラインコンポーネントをスライドインさせる。
- データモデル：追加フィールド不要（既存の`is_wished`/`visited_at`/`location`のみで標高計算可能）。
- URL/ルーティング：`/map`ルートを維持しつつ内部でタイムラインを合成表示（既存の`/timeline`ルートはディープリンク用に残す）。
- パフォーマンス：Google Maps上のオーバーレイ描画はマーカー数が数百件規模なら問題なし、大量データ時はクラスタリングを検討。
- アクセシビリティ：地図が使えない環境（APIキー未設定・オフライン）では既存のリストフォールバックをそのまま維持し、高低差情報はテキストの「気になる度：高」のようなバッジで代替表現する。
- モバイル対応：ピンチジェスチャーはGoogle Maps自体のズームと競合しないよう、専用のズームしきい値を超えた場合のみタイムライン展開をトリガーする設計にする。
- **維持すべき部分**：Google Maps統合、オフラインフォールバックの思想、既存のVenue/Visitデータモデル。
- **捨てるべき部分**：「ちかく」「あしあと」「気になる」を完全に独立したタブとして扱う設計（段階的に統合し、最終的にはタブそのものを削減）。

## 14. 最終決定

### 選択
**B. ふたこと確認（二問収束チューザー）**

### 選ばなかった理由
- **A（潮目）**：スコアも情緒的な魅力も最上位クラスだが、理解可能性(4点)と実装可能性(3点)が低すぎる。PWA・オフラインファースト・既存のRLS/Dexie設計と地続きに作るには前提の作り直しが大きすぎ、"明日から採用"には向かない。長期ビジョンとしてロードマップに残す。
- **C（またねの合図）**：スコア単体では最も高く、プロダクト名との一致という強力なブランド資産になりうるが、核となるジオフェンス検知（店舗圏外離脱トリガー）がPWA/iOS Safariのバックグラウンド位置情報制約と真正面から衝突する。MVPとして簡易代替案（開いた時の距離・時間判定）に落とすと発明の核（"店を出た瞬間"の身体性）が弱まってしまう。
- **D（地形ちかく）**：実装ROIは高いが、単体では新規性・固有性が4案中最も低く、「地図アプリの応用」に見えるリスクを拭いきれない。B案採用後の**Version 1以降で、二問収束の絞り込み結果を地形の上に表示する**形で合流させるのが妥当。

### なぜこの案なのか
1. **現在のプロダクト課題を最も改善する理由**：PRDが明言する最優先指標「未来の意思決定を最短で決める」に対し、現行の「今日どこ行く？」はルールベース1件出しの静的カードに留まっている。二問収束は、Mataneが既に蓄積している`who`/`budget`/`quietness`/`alcohol_tags`という**既存データを一切増やさずに**、意思決定を「探す」から「答えるだけで決まる」に変える。原則1〜3（入力を増やさない・自動取得優先・二段階登録）と完全に整合する。
2. **他サービスとの差別化になる理由**：グルメアプリの多くは「候補を多く見せて選ばせる」設計だが、本案は逆に**1件に収束させて終わらせる**ことを目的化している。これは送客ビジネスと構造的に相性が悪いため、個人の意思決定支援に振り切ったMataneだからこそ成立する。加えて「どの2軸を聞くか」を候補プールの分散から動的に選ぶロジックと、そのために必要なデータの厚みは、後発サービスが同じ体験を再現するには同水準のデータ蓄積期間を要する（模倣耐性の源泉）。
3. **実際に実装する価値がある理由**：新規のテーブル・スキーマ変更が不要で、既存の`Visit`属性と`useSuggestedVenue`ロジックの拡張のみでMVPが作れる。実装可能性8点・MVP到達速度9点と、4案中もっとも低リスクに新規性7点・価値9点を獲得できるバランス点にある。

### 最初の実装
- **1週間以内**：ホームの「今日どこ行く？」カードのタップ先を、固定2問（「誰と？」→「静か／賑やか？」）の二択フローに差し替えるプロトタイプを実装。`useSuggestedVenue`を拡張し、既存の`Visit.who`/`Visit.quietness`でフィルタする純粋関数を`lib/stats.ts`近辺に追加。UIは既存の`ChoiceChips`の見た目言語（amber-400のアクセント）を踏襲した大型二択カードとして実装し、候補数のカウントダウンアニメーションを付ける。
- **1か月以内**：質問順序の動的選択（残り候補群の分散が最も大きい属性を優先的に質問する）を実装し、候補0件時のフォールバック（「気になるに追加する」導線への変換）と、グループ利用時の同時回答マージに対応する。E2E（Playwright）でQ1→Q2→収束のシナリオテストを追加。
- **3か月以内**：二問収束で導かれた1件を、D案（地形としてのちかく）の高低差表示と接続し、「なぜこの店が選ばれたか」を地図上の関係性としても提示できるようにする。あわせてC案（またねの合図）の簡易版（開いた時の距離・時間判定によるrevisit確認バー）を並行導入し、二問収束で選ばれた店を実際に訪れた後の"締め"の体験としてつなげる。
